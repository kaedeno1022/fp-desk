# fp-desk 要件定義

## 概要

FP（ファイナンシャルプランナー）業務支援システム。自分専用ツールとして立ち上げ、実際の顧客対応で使ってから他FPへの提供を検討する。

## 想定利用者

自分専用。他FPへの提供・SaaS化はスコープ外（将来検討課題として残すのみ）。

## 開発方針

将来設計（ライフプランシミュレーション）に機能を絞り、Phase 1（決定論的計算）を先に完成させて実務投入する。顧客管理・モンテカルロシミュレーションはPhase 2以降。一度に作り切って需要・使用感の検証が遅れることを避けるため。

## Phase 1（初期実装）

### ログイン

シンプルな認証。ネット依存を避けるため、自前実装のメール・パスワード認証を用いる（bcryptjs によるパスワードハッシュ化、jose による署名付きJWTセッションCookie）。複数テナント対応や権限分離は行わない。

### 将来設計（ライフプランシミュレーション）— 決定論的計算

税・社会保険・年金・金融計算の詳細仕様は `docs/DOMAIN.md` に定義する。要点:

- 家族情報・収入・支出・資産・負債（奨学金等の既存借入含む）の入力
- ライフイベント登録（結婚・出産・住宅購入・退職等）、年収・生活費の時期変化（賃金カーブ・老後縮小）
- 児童手当・高校就学支援金の自動計上
- 資産の積立期/取り崩し期の自動切替と定率取り崩し（開始年の明示指定も可能）、NISA元本の追跡
- 課税単位は個人。夫婦それぞれに独立した税・社保計算を回し、世帯キャッシュフローは合算表示
- 所得税・住民税・社会保険料の本格実装（現役期・退職後とも同等の精度。退職後は国民健康保険・後期高齢者医療・介護保険第1号・公的年金等控除を含む）
- 住宅ローン（元利均等/元金均等）・住宅ローン控除・NISA/iDeCo/課税口座の区分を含む
- シミュレーション期間中は現在の税制を固定値として計算する（税制改正の予測は行わない。改正時は税率テーブルを手動更新して再計算）
- 公的年金の見込み額は、ねんきん定期便記載の金額をユーザーが手入力する（日本年金機構の計算式は再現しない）
- 資産運用利回り・インフレ率はPhase 1では単純パラメータ（ユーザー入力の固定値、資産クラス別・年次別に指定可能）として扱い、確率変動は行わない
- キャッシュフロー表・資産推移グラフの自動生成（決定論的な単一シナリオの折れ線グラフ）
- 複数シナリオ比較（パラメータを変えた決定論的シナリオ同士の比較）
- シミュレーションは名前を付けて複数保存・呼び出しできる（顧客プロファイルへの紐付けはPhase 2。Phase 2移行時は保存済みシミュレーションを顧客に紐付ける）

### Phase 1 の完了条件

自分の実案件（または自分自身の家計）1件をこのツールでシミュレーションし、既存の手段（手計算・他ツール）と突合して実務投入できると判断できること。

## Phase 2（将来拡張）

- 資産運用利回り・インフレ率のモンテカルロシミュレーション化（確率分布に基づく年次リターンのランダムサンプリング、数千回試行、成功確率・パーセンタイル表示、ファンチャート表示への変更を伴う）
- 顧客管理（顧客プロファイル・面談履歴、シミュレーションを顧客ごとに保存・呼び出し）

## スコープ外（将来検討）

- 他FPへの提供・SaaS化（複数テナント対応、権限分離）
- 提案書PDF自動生成
- 電子署名・書類管理連携
- リマインダー・タスク管理

## 技術スタック

Next.js + SQLite（better-sqlite3）。ネット依存・常駐サーバプロセスを避けるため、Supabase等の外部ホスト型サービスは使わない。認証は bcryptjs（パスワードハッシュ）+ jose（JWTセッションCookie）による自前実装。

## 制約条件・留意点

- 所得税・住民税・社会保険料の税率テーブルは年度キー付きの外部データとして持ち、コードに埋め込まない。税制は毎年改正されるため、テーブル更新だけで対応できる構造にする。数値の投入時は公的機関の公表値と突合し、出典・確認日を記録する（詳細は `docs/DOMAIN.md` §7）
- 住民税は前年所得に基づき翌年課税される（所得税とタイミングが1年ズレる）ため、年次計算ロジックで明示的に扱う
- 被用者の健康保険は協会けんぽ・都道府県別料率を対象とし、健保組合・共済の個別料率は対象外とする。国民健康保険・介護保険第1号は市区町村別のため、居住自治体の料率をユーザーが入力する方式とする（詳細は `docs/DOMAIN.md` §4）
- 計算エンジンはUI・DBから独立した純関数群として実装し、公表値との突合テストを必須とする
- 顧客の資産・個人情報を扱うため、Phase 2で顧客管理を追加する際はアプリケーション層でのアクセス制御（自分専用のため単一ユーザー前提だが、将来の拡張に備えてクエリに必ずユーザーIDでの絞り込みを入れる）を徹底する
- SQLiteファイルは `data/` 配下に保存し、gitignore対象とする（バックアップは別途検討）
